# iPhone approval and return-to-GitHub

Implemented source, not yet a deployed or installable service. The existing Mac configuration stays active until an owner enrolls the iPhone and enables `mobileApprovalSite`.

## Flow

The workflow emits one HTTPS `/native#message=...` link. Its fragment carries the exact canonical approval request, not credentials; it is not sent in the initial HTTP request. An installed, properly provisioned iPhone app can receive this as a universal link. The native app parses only the configured HTTPS origin, exact route and fixed repository, displays the full request, and signs only after explicit review and Face ID. It POSTs the proof to the fixed same-origin `/api/deliver` endpoint. After a confirmed GitHub comment receipt, it opens that exact PR comment automatically. Delivery is not the same as the workflow check becoming green.

If the link stays in a browser, the page offers the configured Apple installation link and a copy/paste path into the app. It cannot reliably detect whether the native app is installed. Same-domain Safari navigation may remain in Safari; user preferences, the source app and Apple's association cache affect universal links. No custom-scheme links are placed in GitHub comments. The Mac web entry uses an ordinary localhost HTTPS-to-HTTP navigation and the existing native app scheme only from its local relay, with the same protocol and endpoints as Native Signing Bridge.

On Mac, run `node mac-relay/server.mjs` on localhost:8787 instead of the earlier signing website, plus `npm start` for the existing delivery service on localhost:8792. Do not run both servers on 8787. This repo now contains the small local relay. It sends the proof through the existing local `gh`-backed delivery service, validates that the returned comment belongs to the exact PR, then replaces the relay page with that GitHub URL. A failed, uncertain or malicious receipt never redirects. Original Mac app installation remains required.

The Home Screen web entry is deliberately not a signing credential. Safari's Share → Add to Home Screen (Open as Web App enabled, where offered) installs it. There is no invented `beforeinstallprompt` or automatic PWA installation. External links are not guaranteed to open a Home Screen app. A PWA WebAuthn implementation could use Face ID or device passcode, and passkeys can sync; UV does not attest biometric-only use or hardware binding. We do not silently add that weaker alternative to the iPhone policy.

## Security boundary

- iPhone creates a P-256 Secure Enclave key with `privateKeyUsage + biometryCurrentSet` and `WhenPasscodeSetThisDeviceOnly`; it requires Face ID availability. Signing uses a fresh LAContext with zero reuse, no passcode OR constraint, and does not silently replace an unavailable key. Changing Face ID enrollment invalidates the protected key. Biometric lockout requires user recovery on the phone.
- A native signature alone does **not remotely attest** the hardware or key ACL. Owner enrollment must compare the fingerprint on the trusted app/device. We have not added App Attest or another hardware attestation protocol. The source enforces the local key policy; server trust remains a pinned public key.
- The existing native wire format is preserved, with exact UTF-8 length framing, DER ECDSA signatures, origin, request ID, nonce, message and short expiry. The workflow additionally binds repository ID/name, PR, exact head/base, action, request and expiry. Replay and revocation gates remain in force.
- `approval/config.json` on trusted `main` is the only enrollment source. The relay fetches it and owner revocation variables live; variable-read errors fail closed. Client and PR-branch records cannot enroll keys. iPhone enrollment is separate from the Mac key. The existing `NATIVE_SIGNER_REVOKED` workflow flag stops both native keys; no workflow permission expansion is needed.
- D1 reserves the workflow request ID atomically before posting. Concurrent calls cannot post twice. An identical retry can return an already-recorded receipt. Ambiguous network writes remain reserved: check GitHub and request a new challenge, rather than blindly reposting. Records contain only request ID, proof hash and confirmed comment URL.
- The relay never supplies a green check; the trusted workflow independently validates the proof. Only that workflow can approve the change. The relay token needs no check-write, code-write, administration or merge permission.
- Return URLs are derived from the verified PR and confirmed GitHub comment, never caller-supplied `return`, `redirect`, `deliver` or query URLs. Native HTTP redirects are disabled when sending the proof.

## Deploy and install

1. Use an owner-controlled HTTPS domain whose `/native`, `/api/deliver` and `/.well-known/apple-app-site-association` are publicly reachable. An authentication-gated private preview is insufficient for Apple's association fetch or native API calls. No domain, hosting resource or Apple purchase has been made. Sites deployment tools were unavailable in this task, so no live URL is claimed.
2. From `relay-site`, run `npm ci` and `npm run build`. Hosting metadata declares D1 binding `DB`; `drizzle/0000_elite_nightshade.sql` is the migration. Sites should provision this binding and apply the migration. The built Worker is `dist/server/index.js`. Do not deploy without the D1 migration. Store `APPROVAL_ORIGIN` and `GITHUB_RELAY_TOKEN` as hosted runtime values, with the latter a secret. `.env.example` is documentation only.
3. Supply a fine-grained PAT restricted to this repo with Contents read, Pull requests read, Checks read, Variables read, Issues write (plus implicit Metadata read). Never embed it in the app, browser, URL, Git history or public record. Do not use Actions' `GITHUB_TOKEN`: its issue-comment writes do not trigger this verification workflow. Token expiration/rotation is an operator responsibility; the code fails closed if it expires. A separately managed GitHub App token can be used if refreshed externally; automatic App-token minting is not implemented.
4. Configure the real Apple team, bundle and domain: `python3 ios/configure.py --origin https://YOUR-DOMAIN --team YOURTEAMID --bundle YOUR.BUNDLE.ID`. This generates an Xcode project, Info.plist, associated-domain entitlement and real AASA file. Add `--install-url https://testflight.apple.com/join/YOURCODE` once distribution exists; the web page then offers that link. Do not publish the `.invalid` default as a working app. Publish AASA as JSON over HTTPS without redirects or authentication. It must contain the provisioned application identifier; verify the App ID prefix with the Apple signing account if it differs from Team ID.
5. Open `ios/TempoApproval.xcodeproj`, choose the signing team, enable the associated-domain capability in the App ID/profile, build on a working Xcode installation, then distribute via an authorized TestFlight/App Store or registered-device route. A local unsigned build is not installable on the user's iPhone. This task's `xcodebuild` failed loading Apple's mismatched IDESimulatorFoundation/DVTDownloads frameworks; repair Xcode separately before archive/distribution.
6. On the physical iPhone, install the signed app, enroll Face ID, open Enroll this iPhone → Show public enrollment record, and have the repository owner compare the full fingerprint directly on that screen. Transfer only the public record. The owner runs `node scripts/enroll-iphone.mjs RECORD.json sha256:FINGERPRINT-READ-FROM-IPHONE` and reviews the resulting config change through the existing trusted approval path. No key was enrolled by this implementation. Existing Mac approval can authorize that change.
7. After config reaches main, request a fresh approval link on a test PR. Test universal-link opening from the actual GitHub app/browser, Face ID cancel/success, unavailable/changed Face ID, automatic confirmed return, expired request, changed commits, retry after a dropped response, and iPhone revocation. Do not merge a real change merely to test the UI.

Emergency revocation uses the existing administrative procedure: `npm run revoke -- iphone`. It first locks merges, then sets the existing NATIVE_SIGNER_REVOKED variable, disabling both iPhone and Mac native approvals. This conservative shared emergency stop preserves the existing workflow. For an iPhone-only permanent removal, remove the iPhone record through owner review while merges remain locked, then follow the owner recovery process. This command was extended but **not run**. Removing a key or setting a variable alone does not invalidate an already-green check; preserve the existing lock-first procedure and owner recovery.

## Verified here

- 63 Node tests: real P-256 signatures, exact-action validation, old Mac regressions, D1 behavior through a real SQLite adapter, concurrent/ambiguous delivery, revocation, URL rejection and local HTTP boundaries.
- Five Swift core tests: strict message parsing, origin/link handling, UTF-8 framing and exact-PR delivery receipts.
- All iOS app files type-checked against the actual iOS 26.5 SDK targeting iOS 17.
- A Swift CryptoKit software-key signature was accepted by the Node exact-action verifier. This establishes wire compatibility, not Face ID or Secure Enclave E2E.
- Relay production build, TypeScript and lint checks; local built-Worker smoke checks returned HTTP 200 for the entry/manifest and HTTP 503 for unconfigured delivery. Dependency security updates removed all high-severity audit findings; four moderate development-tool findings remain in the Drizzle/esbuild chain, which is used for schema generation and is not shipped as the Worker runtime. No force-downgrade was applied. The optional CI definition is saved at `ci/iphone-tests.yml`; installing it under `.github/workflows/` requires workflow scope, which the current GitHub OAuth credential lacks. No physical-iPhone, universal-link, real hosted relay, GitHub delivery or Face ID ceremony was performed. Browser UI QA was not requested. This background task did not open a user-facing preview.
